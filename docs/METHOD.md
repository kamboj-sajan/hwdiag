## Shared conventions

- **One result format.** Every tool writes one JSON object: `format_version` (1), `tool`,
  `tool_version`, `timestamp` (UTC), `git_commit`, `host`, `params`, `results`, `warnings`.
  `host` records what changes the numbers: CPU model, kernel, frequency governor, turbo, SMT,
  compiler and the exact compiler flags. `harness/hwdiag/schema.json` (JSON Schema 2020-12)
  checks the envelope strictly and each tool's `results` by tool; the harness validates every
  file it reads or writes.
- **Exit codes.** 0 = ok, 1 = usage or runtime error, 2 = ran fine but found a problem (an
  inventory check failed, memtest found errors, stress saw throttling, `run` had a tool report
  a problem). `compare` exits 1 on a regression so CI can gate on it.
- **Units.** Sizes in bytes (K/M/G are binary: KiB, MiB, GiB). Bandwidth in GB/s = 10^9 bytes
  per second, as STREAM reports it. Latency in ns per load. Temperatures in °C; sysfs reports
  millidegrees, so `45000` is 45 °C.
- **Testability.** Every parser of `/proc` and `/sys` takes a root directory. The tests point it at
  fake trees in `tests/fixtures/sys/` (a desktop and a two-socket server), generated by
  `tests/fixtures/make_sys_fixtures.py`.

## inventory

Reads `/proc/cpuinfo` (model, flags), `/sys/devices/system/cpu/cpu*/topology/` (sockets = distinct
`physical_package_id`; cores = distinct package/die/core triples; threads = CPUs),
`cpu0/cache/index*` (level, type, size, line size), `cpufreq/scaling_cur_freq` (kHz),
`/proc/meminfo`, `/sys/devices/system/node/`, PCIe link attributes under
`/sys/bus/pci/devices/*`, hwmon sensors and EDAC counters.

Checks:

| Check | Rule | Level |
|---|---|---|
| PCIe link | current speed below max speed, or current width below max width | warn, "re-check under load" |
| Temperature | any hwmon temperature above `--temp-threshold` (85 °C) | warn |
| Memory errors | any EDAC `ce_count` or `ue_count` above 0 | fail |
| No EDAC / no sensors / no link status | nothing to judge | info |

Limits:

- **PCIe links slow down on purpose.** GPUs and many NICs drop to 2.5 GT/s (Gen 1) at idle to save
  power (ASPM and driver power states), so a warning at idle is expected. Re-run the inventory
  while the device is busy before calling it a fault. Devices with no link attributes (host
  bridges, virtual devices), an `Unknown` speed or width 0 (link down) are skipped.
- **EDAC needs a driver and ECC memory.** Desktops without ECC, and VMs, have no
  `/sys/devices/system/edac/mc`; the inventory says so instead of reporting zero errors.
- **hwmon names are driver-specific** (`coretemp`, `k10temp`, `nvme`, `nct6775`, ...). The threshold
  applies to all temperature inputs, including NVMe drives, which run hotter than CPUs.

## memlat: latency

**The chain.** The buffer is cut into 64-byte lines. Sattolo's algorithm shuffles the line
indices into a single random cycle: like Fisher–Yates, but `j` is drawn from `[0, i-1]` instead of
`[0, i]`, which makes every permutation with more than one cycle impossible, so following the
links from any line visits every line before returning. Line `i` stores the address of line
`perm[i]`. The loop is `p = *(void**)p`, unrolled 16 times; each load needs the result of the one
before, so loads can't overlap and the time per step is the full load-to-use latency. The final
pointer is written to a `volatile` variable so the compiler cannot delete the loop.

**Why random.** A sequential walk is caught by the hardware prefetchers, which fetch the next
lines before they are asked for and hide most of the latency (the `sequential/4k` curve shows
this: a few ns even at DRAM sizes). A random cycle gives them nothing to predict.

**Timing.** `clock_gettime(CLOCK_MONOTONIC_RAW)`, which NTP does not slew. Per size:

1. `mmap` a 2 MiB-aligned buffer and set its page size (below).
2. Build the chain. Writing the links touches every page, so first-touch page faults happen here,
   not inside a timed region.
3. One warm-up lap of at least the whole chain. It also estimates the latency, from which the step
   count is chosen so one repetition takes about `--target-ms` (100 ms; 20 ms in the quick suite),
   at least 16,384 steps, rounded to a multiple of 16.
4. `--reps` timed repetitions (default 7, at least 5). The pointer carries on round the cycle
   from one repetition to the next. The result is the median, with min, max, standard deviation
   and spread `(max − min) / median`.

The thread is pinned to one CPU (`sched_setaffinity`) for the whole run.

**Pages.** `--pages 4k` calls `madvise(MADV_NOHUGEPAGE)` so a system with transparent huge pages
set to `always` doesn't silently give 2 MiB pages. `--pages huge` calls `madvise(MADV_HUGEPAGE)`
before first touch, and the tool reads `AnonHugePages` for the buffer from `/proc/self/smaps`, so
the result says whether huge pages actually backed it (THP can be disabled or memory too
fragmented).

**Boundaries.** A boundary is a latency rise of more than 1.5× between neighbouring sizes. Runs of
consecutive rises are merged into one boundary, because a transition usually spans two or three
sizes. The detected cache size is the last size before the rise. Boundaries are then matched to
the sysfs Data/Unified caches **in order** (first step with L1, next with L2, ...), keeping as many
pairs as possible and the closest sizes. Matching by nearest size alone fails in a VM: the host's
L3 is shared by many guests, so the effective L3 step comes far below the sysfs size and would be
paired with L2.

**What else makes steps.** With 4 KiB pages the data TLB also runs out: a typical first-level dTLB
covers 64 × 4 KiB = 256 KiB and the second-level TLB about 1,536–2,048 entries (6–8 MiB). Past
those sizes every load may need a page walk, adding latency that has nothing to do with the cache
sizes. With 2 MiB pages the TLB covers hundreds of MiB to GiBs, so the `random/huge` curve
isolates the cache steps; that curve is used for `detected_caches` when it was measured. The
difference between the two curves at large sizes is the cost of TLB misses.

**Limits.**

- Caches are not ideal LRU, and set associativity plus random physical page placement cause
  conflict misses before the nominal capacity, so the latency rises a little before each
  boundary. An exclusive or non-inclusive L3 makes the effective capacity L2 + L3.
- In a VM the L3 is shared with other tenants and the numbers move with their load.
- Frequency matters: with the `powersave` governor or turbo, ns per load changes with the clock.
  Every result records the governor and turbo state.
- The DRAM figure (`dram_latency_ns`) is the median at the largest size on the `random/4k` curve,
  as specified. It includes page walks; the `random/huge` value at the same size is closer to the
  raw DRAM latency.

## membw: bandwidth

**Kernels** (STREAM, doubles): copy `c = a`, scale `b = 3c`, add `c = a + b`, triad `a = b + 3c`.

**Sizes.** Each of the three arrays is at least 4× the last-level cache from sysfs and at least
64 MiB, so the data cannot stay in cache. If the arrays would take more than half of `MemAvailable`
they are shrunk, with a warning.

**Threads.** 1 to N (N = CPUs the process may use), or 1, 2, 4, ..., N above 16. Workers are
pinned in an order that uses every physical core before any SMT sibling. For each thread count the
arrays are mapped fresh and each worker first-touches its own contiguous slice, so on a
multi-socket machine its pages are on its own NUMA node.

**Timing.** A spin barrier releases all workers at once; the time is measured from the start
barrier to the end barrier by worker 0, which is the calling thread. (A separate coordinating
thread spinning on the barrier competes with the workers for a CPU: in development on the 4-vCPU
VM it made the 4-thread result lower than the 3-thread one.) One untimed warm-up pass, then
`--reps` timed passes of the
four kernels (10 in the full suite). Reported: best (max), median and every sample.

**Bytes.** Counted the STREAM way: copy and scale 16 bytes per element (one read, one write), add
and triad 24 (two reads, one write).

**Write-allocate.** A normal store to a line not in cache first reads the line from memory
(read-for-ownership), then writes it back later. So copy actually moves 24 bytes per element (read
`a`, read `c`, write `c`), not the 16 it is credited with. The real DRAM traffic is 1.5× the
reported figure for copy and scale and 1.33× for add and triad. Non-temporal (streaming) stores
avoid the read; that is why the kernels are compiled without loop-idiom recognition: otherwise GCC
and Clang turn the copy loop into a `memcpy` call, and glibc's `memcpy` uses non-temporal stores
for large copies, which would make copy measure something different from the other kernels.

**Validation.** After the timed passes every element is checked against the STREAM recurrence
(relative error ≤ 1e-13), which proves each kernel ran over the whole array.

**Stress mode.** `--duration S` runs triad on every CPU and prints one JSON line per interval with
the GB/s achieved in that interval. The clock starts after every worker has first-touched its
slice.

## perfctr: hardware counters

**Opening.** `perf_event_open` through `syscall(SYS_perf_event_open, ...)` (glibc has no wrapper),
for the calling thread on any CPU (`pid = 0, cpu = -1`). Events: cycles, instructions,
cache references, cache misses, branch misses (all `PERF_TYPE_HARDWARE`), L1D read misses and
dTLB read misses (`PERF_TYPE_HW_CACHE`). `exclude_kernel = 1` and `exclude_hv = 1`, so only user
code is counted (this is also what lets a normal user count at `perf_event_paranoid = 2`).

**One group.** All events are opened as one group led by cycles: the leader starts disabled,
members follow it, and the group is read in one `read()` with
`PERF_FORMAT_GROUP | TOTAL_TIME_ENABLED | TOTAL_TIME_RUNNING | ID`. A group is scheduled onto the
PMU all together or not at all, so its counts cover exactly the same instructions and ratios such
as IPC are consistent. `start()` resets and enables the group (`PERF_IOC_FLAG_GROUP`); `stop()`
disables and reads it. Reset clears the counts but not the times, so the times are deltas from a
reading taken at `start()`.

**Multiplexing and scaling.** When more events are requested than the PMU has counters, the kernel
rotates groups on and off the hardware. Each group then reports `time_running < time_enabled`,
and the count is scaled up: `estimate = raw × time_enabled / time_running`. The reading reports
the scale factor and a `multiplexed` flag. The estimate assumes the workload behaves the same
while the group was off the PMU; for a steady loop that holds well, for a bursty one it doesn't.

**Group splitting.** Seven events often don't fit in one group. Intel cores have three fixed
counters (instructions, cycles, reference cycles) plus 4 general counters per hardware thread with
Hyper-Threading on (8 with it off); AMD Zen has 6 general counters and no fixed ones; the NMI
watchdog may hold one more. A group that can never fit is either rejected at open time (x86
validates groups and returns `EINVAL`) or opens and is never scheduled (`time_running` stays 0, all
counts read 0). perfctr handles both: an `EINVAL` when joining a group starts a new group led by
that event, and a short probe after opening checks every group ran; if one didn't, everything is
reopened in smaller groups, each led by its first event. The kernel then multiplexes the groups
and the scaling above applies.

**Unavailable.** `EACCES` and `EPERM` (`perf_event_paranoid` too high, or a container's seccomp
filter), `ENOENT` (event or PMU missing; VMs usually expose no CPU PMU), `EOPNOTSUPP`, `ENODEV` and
`ENOSYS` mean "unavailable": the group records the reason, `start()`/`stop()` do nothing and the
tools write `null` counters. If only a non-leader event fails, that event is dropped and the rest
kept. Nothing throws. The system calls are injectable, and the tests drive a fake kernel through
every errno, both splitting cases, multiplexing and the scaling arithmetic.

**Cross-check.** `perfcheck` starts a group at the top of `main`, runs a fixed workload (an
arithmetic loop plus a pointer chase, about one second), and stops at the end. The harness runs it
under `perf stat -x, -e cycles:u,instructions:u` and stores the % difference between perfctr's
counts and perf stat's for the same process. They should agree within a few percent; perfctr
counts slightly less because perf stat also sees the dynamic loader, static initialisers and the
JSON output. Tolerance: 5%.

**Limits.** Hybrid Intel CPUs (P-cores and E-cores) have two PMUs; generic hardware events open on
one of them, so pin to a P-core (CPU 0 usually is) when counting. Counts are per thread; membw
opens one group per worker and sums them.

## memtest: memory test

**Buffer.** 25% of `MemAvailable` by default, `mmap`ed and locked with `mlock()` so it can't be
swapped out mid-test. If `mlock` fails (the default `ulimit -l` is small) the tool warns, carries
on unlocked and records `locked: false`; raise the limit with `ulimit -l unlimited`.

**Patterns and the faults they target.**

| Pattern | What it does | Fault classes it targets |
|---|---|---|
| zeros | write 0 everywhere, read back | bits stuck at 1 |
| ones | write all-ones, read back | bits stuck at 0 |
| checkerboard | 0x55… / 0xAA… in alternating words, then inverted | coupling between neighbouring bits and cells, leakage between cells |
| walking ones | pass k: word i holds a single 1 at bit (i + k) mod 64; 64 passes | data-line (DQ) faults: stuck or shorted data lines, bridging between bits |
| walking zeros | the inverse: a single 0 walks through every bit | the same with the opposite polarity |
| address-in-address | each word holds its own address, then the complement | address-line faults: stuck or shorted address lines, two addresses landing on the same cell (aliasing), decoder faults |
| moving inversions | write p upward; upward: check p, write ~p; downward: check ~p, write p; for p = 0 and 0x5555… | transition faults (a cell that can't go 0→1 or 1→0) and coupling faults where writing one cell disturbs a cell above or below it (the up and down passes catch both directions) |
| random | splitmix64 data from a recorded seed, then its complement | pattern-sensitive faults that regular patterns miss |

Every mismatch is logged with the pattern, byte offset, expected and actual values, XOR mask and
the list of flipped bits; the physical address is added when `/proc/self/pagemap` allows it (root
only). The first 1,000 errors are stored, all are counted. A compiler barrier between each write
phase and its check makes the check really read memory back.

**Fault injection.** `--inject-fault <offset>:<bit>` (offset a multiple of 8, bit 0–63) flips one
bit once per pattern, after the pattern's first write phase and before its first check. The unit
tests run every pattern with faults in the first, a middle and the last word and require exactly
one error with the right offset, expected value, actual value and mask; without a fault every
pattern must find nothing. This is mutation testing for the tester: a pattern that can't see a
flipped bit it was told about is broken.

**Honest limits.**

- A user-space test only checks the memory the kernel hands it. The rest of RAM (kernel, other
  processes, page cache) is never tested.
- Caches can hide faults: a value read back while still in cache never went to DRAM. The buffer is
  far larger than the caches so most reads come from DRAM, but not all.
- ECC memory corrects single-bit errors before the program sees them; on ECC machines check
  the EDAC counters (`hwdiag inventory`) after a run.
- No delays between write and read, so retention (leaky cell) faults are mostly missed; no row
  hammer patterns.
- It demonstrates the method. It does not replace memtest86+, which runs before the OS and tests
  almost all of physical memory.

## The harness

- **run.** `quick` (CI, about a minute): memlat to 64 MiB, 5 repetitions of 20 ms, all three
  curves; membw with 3 repetitions; memtest on 64 MiB; perfcheck with a short workload. `full`:
  memlat to 1 GiB, 7 repetitions of 100 ms, all curves; membw with 10 repetitions; memtest on 25% of
  available memory; and, on machines with more than one NUMA node, memlat pinned to the first CPU
  of node 0 with memory bound (`set_mempolicy`, `MPOL_BIND`) to each node in turn.
- **compare.** Metrics, each with a direction: memlat L1/L2/L3/DRAM latency per curve (the point at
  the largest size at most half of each sysfs cache size, well inside the level; DRAM at the
  largest size; a level is skipped when its point would be the DRAM point), membw best GB/s per
  kernel and thread count, and memtest errors (any increase is a regression, whatever the
  tolerance). The table shows the run-to-run spread next to each change.
- **stress.** Throttling means the frequency fell while the load stayed the same: the 5-sample
  rolling median of the mean CPU frequency stays more than 10% below the baseline (median over the
  first 30 s) for at least 5 consecutive samples while CPU utilisation stays at 90% or more. A rise
  in Intel's `thermal_throttle` counters also counts. Frequency, temperature and bandwidth are
  drawn as three charts sharing the time axis, never two scales on one chart.

## Telling a real slowdown from noise

1. **Control the conditions** that move the numbers and are recorded in every result: governor
   (`performance`), turbo, SMT, pinning, other programs, thermal state, kernel and compiler flags.
   `compare` warns when the CPUs differ.
2. **Look at the spread.** Each metric is a median of repeated measurements with its spread. A
   change smaller than the spread of the runs is not evidence of anything. `compare` prints the
   combined spread of both runs next to each change.
3. **Measure the noise floor.** Run the baseline two or three times and compare them with each
   other; set `--tolerance` above the differences seen between identical runs. On the shared cloud
   VM in [results/cloud-vm](../results/cloud-vm/), the spread between the fastest and slowest
   repetition (`spread_pct`) has a median of 12% across memlat sizes (interquartile range 7–20%)
   and 24% across membw kernels (15–35%), so a 5% tolerance would flag noise there. A quiet
   bare-metal machine with a fixed governor is much tighter.
4. **Check that it reproduces** on a second run, and that related metrics move together (a DRAM
   latency regression should show in the huge-page curve too; a bandwidth regression across all
   four kernels points at memory, one kernel at code generation).
5. **Use the counters.** If time per load rose but cycles per load did not, the clock slowed down
   (frequency, throttling), not the memory system. Rising dTLB misses per load point at page size,
   rising L1D misses at layout.
6. For a formal answer, compare the two sets of samples with a rank test such as Mann-Whitney U
   rather than two medians.

## Decisions where the spec was open

- JSON is written by a small in-house writer (no external library, so nothing to download).
- Inventory checks have an `info` level for "nothing to judge" (no EDAC, no sensors, no link
  status), so a VM is `ok` rather than `warn`.
- memlat: at least 16,384 steps per repetition; chain seeds are `seed + size` so each size gets its
  own cycle; sizes over half of `MemAvailable` are skipped with a warning; consecutive jumps merge
  into one boundary; boundaries are matched to cache levels in order (see above).
- perfctr: the `EINVAL` split at open time in addition to the probe split.
- membw: the calling thread is worker 0; fresh arrays per thread count; arrays at least 64 MiB;
  at most 200 repetitions (the STREAM values grow 15× per pass and would overflow a double after
  about 260).
- memtest: offsets in `--inject-fault` are byte offsets aligned to 8 and bits are 0–63 in that
  64-bit word; the fault fires once per pattern, so each pattern reports exactly one error.
- Harness exit codes follow the tools (0/1/2); `run` keeps going when one tool fails and records
  its exit code in `run.json`.
- Charts use a categorical palette checked for colour-blind separation; colours are fixed per
  curve and kernel, lines are labelled at their ends and every chart has a table in `REPORT.md`.

## Interview questions

**Why does latency jump at certain sizes? What do the L1/L2/L3/DRAM steps tell you?**
Each plateau is the latency of the smallest level the working set fits in; a step is where the
working set outgrows a level and loads start missing to the next one. The position of a step
estimates that level's effective capacity, and the height of each plateau is its load-to-use
latency (a few cycles for L1, roughly 12–16 for L2, 40–70 for L3, 80–120 ns or more for DRAM on a
desktop). Steps come a little before the nominal size because of associativity, replacement policy
and physical page placement, and an extra step can appear where the TLB runs out.

**Why random pointer chasing instead of a simple loop? What do the prefetcher and the TLB do?**
A simple loop has independent loads that the core overlaps (many misses in flight at once) and a
predictable address stream the prefetchers fetch ahead of time, so it measures throughput with
the latency hidden. Pointer chasing makes each address depend on the previous load, so only one
miss is in flight, and a random single cycle (Sattolo) defeats the prefetchers. The TLB caches
virtual-to-physical translations; when the working set spans more pages than it covers, loads also
pay for a page walk, which the 4 KiB vs huge-page comparison makes visible.

**How do CPU hardware counters work, and what is counter multiplexing?**
The PMU has a few programmable counters (plus some fixed ones) that count events such as cycles,
retired instructions and cache misses. `perf_event_open` asks the kernel to program them for a
thread; the kernel saves and restores them on context switches. When more events are requested than
counters exist, the kernel time-slices groups of events onto the hardware and reports how long
each was enabled and actually running; the tool scales counts by enabled/running to estimate the
full-time value. Events in one group are always scheduled together, so their ratios are exact.

**Which memory faults does each test pattern catch?** See the table in
[memtest](#memtest-memory-test): solid patterns for stuck bits, checkerboard for neighbour coupling,
walking bits for data lines, address-in-address for address lines and aliasing, moving inversions
for transition and coupling faults in both directions, random data for pattern-sensitive faults.

**What is PCIe link training, and why might a link run below its maximum?**
After reset, the two ends of a link run the LTSSM (Link Training and Status State Machine): they
detect each other, agree on lane width and polarity, and then step up to the highest speed both
support that the channel can carry reliably (equalisation at 8 GT/s and above). A link can come up
slower or narrower because of power management (GPUs and NICs drop to Gen 1 at idle), a slot that
is physically x16 but wired x4 or shared (bifurcation), a riser or cable that degrades the signal,
BIOS settings, or a marginal channel that fails equalisation at the higher speed. Idle downtraining
is normal; the same reading under load is a fault.

**How would you tell a real slowdown from measurement noise?** See
[the section above](#telling-a-real-slowdown-from-noise): control and record the conditions, repeat
and report the median with its spread, measure the run-to-run noise to set the tolerance, confirm
it reproduces and that related metrics agree, and use the counters to find which part moved.
